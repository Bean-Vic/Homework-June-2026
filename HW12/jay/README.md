## Task 7 Summary (Index and Query Performance Lab)

Experiment: seeded 5,000 documents into the `perf_tasks` collection and compared `explain('executionStats')` before and after creating indexes.

| Query | Before index | After index |
|---|---|---|
| `{ status: 'todo' }` | COLLSCAN, examined 5000 docs | IXSCAN(status_1), examined 1667 docs |
| `{ status, dueDate range } + sort(dueDate desc)` | SORT + COLLSCAN, examined 5000 docs | IXSCAN(status_1_dueDate_-1), examined only 240 docs, **and no in-memory sort needed** |
| `{ dueDate range }` alone | COLLSCAN | still COLLSCAN (cannot use the compound index) |

**1. Which query became faster?**
The `status` equality query dropped from a full collection scan (5000 docs) to examining only the 1667 matching documents. The `status + dueDate` range query benefited the most from the compound index `{ status: 1, dueDate: -1 }`: docsExamined went from 5000 → 240, and the SORT stage disappeared from the explain output — the index is already ordered by dueDate descending, so the in-memory sort is eliminated.

**2. Why does compound index field order matter?**
Compound indexes follow the **leftmost prefix rule**: `{ status: 1, dueDate: -1 }` is like a phone book sorted first by status, then by dueDate. Queries on `status` (the prefix) or on `status + dueDate` can use it; but a query on `dueDate` alone gets no help (still COLLSCAN in the experiment), because without status, dueDate values are not stored contiguously in the index. So put equality-filter fields first and range/sort fields after.

**3. Why do too many indexes hurt writes?**
Every insert/update/delete has to maintain **every** index on the collection in addition to writing the document itself (B-tree node inserts/deletes, possible page splits). Ten indexes turn one write into 1 document write + 10 index updates, and they also consume more memory and disk. So only create indexes for real, high-frequency queries, and be especially restrained on write-heavy collections.

**Extra**: with a unique index, duplicate inserts throw `E11000 duplicate key` (code 11000); reading 2000 docs x5 took ~35ms with `lean()` vs ~81ms with regular hydrated documents — `lean()` is over twice as fast for read-only scenarios because it skips Mongoose Document instantiation overhead.
